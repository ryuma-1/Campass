# Testing

No test suite or test framework is set up yet. Do not add a test framework (e.g. RSpec, Jest) without the user's approval, because it is a new dependency.

## What must be tested once implemented

From `docs/design_doc.md` section 7:

- **Map structure**: JSON Schema validation of LLM output, plus detection of cycles in `map_paths`, `sub_node_paths` and `sub_nodes`, unknown references, main nodes that cannot reach the goal (the last main node; this covers orphan nodes), and a main node count outside the `node_count_target` range.
- **Node reuse**: reused nodes are not duplicated, keep their progress, added sub nodes show up in other maps, and another user's nodes cannot be referenced. With a fixture where a reused node rewrites its existing sub nodes, `sub_nodes` and `sub_node_paths` are not duplicated, and existing ones left out of the output are not deleted.
- **Regeneration (design_doc 4.2.4)**: with an LLM stub that returns output failing validation, the regeneration request carries the previous output and the validation errors as a conversation, and retries stop after 2. Whether regeneration can run after nodes are saved is open (design_doc section 9).
- **Compass**: for maps in different progress states (nothing started, partly completed, several `in_progress`, only sub nodes completed, all completed) and graphs with branches and merges, check `current_node_id`, `candidates` (contents and order), and `is_goal_reached`. For shared nodes: known nodes drop out of candidates and satisfy incoming paths, nodes started in this map stay candidates, and `started_map_id = NULL` is not known.
- **Progress update**: only the acting map's current position moves; resetting the node at the current position moves it back to the previous started or completed node; goal reached with an origin node returns a suggestion and never auto-completes it.
- **Node editing (F-018)**: edits that make `map_paths`, `sub_node_paths` or `sub_nodes` cyclic return `422 cycle` and save nothing. Removing the node at the current position moves it back, and a node placed again does not reuse its old events; removing every main node returns to the start point and is not goal reached. Removing a main node deletes its paths and detour and deletes only nodes left unreferenced. Edits reaching other maps or deleting nodes with progress return `409 confirmation_required` and change nothing without `confirmed=true`. Edits on non-`ready` maps return `409 map_not_ready`; another user's nodes cannot be placed or edited. Suggestions return only the user's nodes with correct `already_main` and `inside`. In a map made from an origin node, placing or removing a main node changes the origin node's sub nodes the same way. Two edits of the same node from two places: the later save is kept and neither gets `409`.
- **S-03 sync (`docs/design_doc.md` section 4.4)**, with fixed JSON responses and an injectable clock: `visibilitychange` to `visible` and `window` `focus` each refetch `GET /api/maps/:id`, both within 2 seconds refetch once, and nothing refetches periodically; the sidebar list uses the same trigger. The map and compass are replaced while viewport and zoom stay; an open detail panel is refetched; a removed selected node closes the panel, drops `?node=` and shows 「このノードはマップから外されました」; unsaved input on a node changed elsewhere is kept with 「このノードは別の場所で変更されました」 and 「入力を捨てて最新を表示」 (no notice if unchanged); `404` moves to the latest map or S-02 with the deletion notice.
- **CLI editing**: on `409 confirmation_required` the CLI asks `y/N` and resends with `confirmed=true` only on `y`; `--new` skips suggestions.
- **CLI version and API URL (`docs/design_doc.md` sections 4.5.1 and 4.5.2)**: `campass version` prints the embedded version, or `dev` without one; every request has `User-Agent: campass-cli/<version>`; `CAMPASS_API_URL` overrides the embedded default URL.
- **CLI login (`docs/design_doc.md` sections 4.5.4 and 7)**: with an `httptest` server returning `…/token` responses in order, `authorization_pending` keeps polling every `interval`, `slow_down` adds 5 seconds, `access_denied` and `expired_token` print their message and exit, `200` saves the token (0600), and Ctrl+C while waiting prints a newline and exits with 130. The wait is injectable so tests never sleep; the URL and code are printed even if the browser cannot be opened. On `401` `token_expired` / `invalid_token` the CLI prints its message, deletes the token file and exits with 1, and never starts `campass login`.
- **CLI login (backend)**: `…/token` returns each of the four states and success under the right conditions; the token is returned only once, then `expired_token`; no plaintext `device_code` or token is stored; `lookup` / `approve` / `deny` return `401` without a Web login or with a Bearer token, and `404` for expired or non-`pending` requests. Token lifetime (with an injectable clock): issued `expires_at` is +30 days, use extends it, no write within a day of the last update, 30 days unused → `401 token_expired`, revoked or unknown token → `401 invalid_token`.
- **Difficulty mapping**: ライト / スタンダード / ディープ produce the intended `max_depth`, `node_count_target` range and sub node count guide (design_doc 4.2.2).
- **Streaming (E2E)**: with an LLM stub that streams a fixed fixture node by node, drop the SSE connection mid-generation and check that the job keeps running to `ready`; reconnecting with the same `GET /api/maps/:id/generation` resends all saved nodes, then new ones, then `done`; resent nodes are not drawn twice (upsert by node ID); nodes received so far still show correctly, also after reloading S-03; no compass before `done`; a job failure ends with `error` and the failed view; deleting a generating map in another tab ends with `deleted`, a move to the remaining map with the latest `updated_at` (or S-02 if none) and the deletion notice (`docs/design_doc.md` sections 4.2.9, 4.3.1, 4.4).
- **Generation job (backend, `docs/design_doc.md` section 4.2.9)**, in Minitest (Rails default, no new gem) with no real LLM call:
  - Behaviour: a `generating` map past the heartbeat limit (5 minutes) becomes `failed` / `timed_out` from the SSE loop, `GET /api/maps` and `GET /api/maps/:id`, and stays `generating` just before it (e.g. 4:59). A node save and a map deletion at the same time write all or nothing of one node; if the deletion wins, the job closes the LLM stream, ends quietly without `failed`, and adds no sub nodes to shared nodes. A late job after `timed_out` checks `status` and saves nothing. An exception stores `status = failed` and `generation_error_code`; the exception message reaches the log only, never the DB or a response. SSE `error` and REST `error.message` come from the same code → message table. Deleting a generating map follows the deletion rule (design_doc 4.1.2).
  - Time: `travel_to` / `travel` (`ActiveSupport::Testing::TimeHelpers`), never real waits. The heartbeat limit is a setting; tests build the boundary from it.
  - Concurrency: fix the order instead of waiting for a race. Run the job in a thread and pause it right after it locks the `maps` row (a test-only hook, e.g. `Concurrent::Event` from `concurrent-ruby`, bundled with Rails); start the deletion on the main thread and check it waits for the lock; resume the job and check the whole node is saved before the deletion proceeds. Also test the reverse order (deletion locks first). Run on the real MySQL (Compose `db`), since row locks are a DB feature; turn off `use_transactional_tests` for these tests only (two threads use separate connections) and clean up the data they created.
  - LLM stub: the job takes its LLM client from outside. The fake streams the E2E fixture node by node, can raise mid-stream, and records whether `close` was called.
- **Map `updated_at`**: generation (node saves, `status` changes), progress updates and edits made from a map touch that map's `updated_at`; another map containing the same nodes is never touched by shared edits, progress updates, sub nodes added by reuse, origin-node sub node changes or nodes deleted with a map; `GET /api/maps` sorts by `updated_at` desc, then `id` desc.
- **Map deletion**: nodes used by other maps keep their progress; unreferenced nodes are deleted.
- **Web auth (F-019, `docs/design_doc.md` section 4.6)**, with omniauth mocks (never the real Google / GitHub): first login creates the user and identity, and later logins find it by `provider` + `provider_uid` even if the email changed; a matching verified email merges into the existing user, no verified email means no login and no user; `return_to` such as `//evil.example.com` or an absolute URL becomes `/maps`, and the redirect origin is always `FRONTEND_ORIGIN`; Cookie-session writes without the CSRF token or with another `Origin` get `403` and change nothing, Bearer requests pass; a session unused for 30 days gets `401`, using it extends it (no write within a day of the last update); logout deletes only that device's session; CORS is not granted to origins other than `FRONTEND_ORIGIN`; only the token digest is stored.
- **Security**: API keys are absent from frontend responses and source maps. No-training is kept by the API plan, not by the request, so it is checked in the deploy steps, not by tests (`docs/design_doc.md` section 4.3.2).

## LLM calls in tests

Unit tests must not call the real LLM API. Use fixed JSON fixtures for LLM responses.

Rewriting a reused node's full contents and regeneration with the previous output were never run against the real Gemini, even in the prototype. Check them by hand with real calls after implementing (design_doc section 7).
