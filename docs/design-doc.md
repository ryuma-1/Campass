## 1. コンテキストとスコープ

独学者は「最終的に何ができるようになりたいか（ゴール）」は漠然と持っていても，そこに至るまでの前提知識の依存関係を自力で把握することが難しく，基礎学習の途中で「これが何に繋がるのか分からない」まま離脱してしまうケースが多い（ReqDef 2.1）．また，表面的なツールの使い方（ハウツー）の習得に偏り，背後にある原理原則の理解に到達しないまま学習が止まってしまう問題もある．

Campass は「トップダウン逆算型ボトムアップ学習」，すなわちゴールから逆算して必要な前提知識を洗い出し，基礎から順に積み上げていく学習プロセスを LLM に計算させることで解決を図る．計算された依存関係は本質的にグラフ（ネットワーク）になりやすく，そのまま提示すると「今何をすべきか」が分かりにくい．また，独学者は「AIも学びたいがデザインにも興味がある」のように複数のゴールを並行して抱えることが多く，ゴールごとに別々のグラフを作ると同じ内容を2回学ぶことになる．

本書のスコープは，次の3点を無理なく成立させる設計の理由である．

1. LLM によるマップ（グラフ構造）の構造化データの生成と，既存ノードの再利用．
2. マップのグラフをそのまま提示しつつ，進捗から現在地と次に学べるノードを導出すること．
3. ノードの内容と進捗をマップ間で共有しながら，マップごとの位置づけ（道・重要度）を分けて持つデータモデル．

## 2. 目標と非目標

### 2.1 目標

* ゴールごとの「マップ」を地図のように俯瞰でき，マップ上では「コンパス」が学習者の現在地から次に学べるノードを指し示す．「地図を広げ，コンパスで進む方向を確かめながら学ぶ」というのが本アプリ（Campass）のコンセプトである．
* 複数のマップに同じ内容が出てくる場合はノードを共有し，他のマップで学んだことが今のマップでも土台になっている状態にする．
* 生成に数十秒かかっても，学習者が最初の一歩をすぐに読み始められる（ReqDef 5.2）．

### 2.2 非目標

* **独自LLMの学習・ファインチューニング**: 既存の外部LLM API を利用する前提とし，モデル自体の開発は行わない（ReqDef 3.2）．
* **教材コンテンツそのものの制作**: 各学習ステップの本文教材を自社で執筆・作成することは行わない．外部記事へのリンク提示とAIによる概要生成，課題提示に留める（ReqDef 3.2）．
* **Pixel Perfect なUI定義**: 画面レイアウトの厳密な仕様は Figma 等の別ドキュメントに委ねる．
* **要件の再定義**: 要件の是非は ReqDef.md で確定済みとし，本書では「その要件をどう実現するか」の理由だけを議論する．
* **仕様の記述**: 仕様は基本設計書に書き，本書には再掲しない．

## 3. 設計の概要

設計の核になるトレードオフは次の4つである．各節の詳細は4章に書く．

1. **グラフのまま見せ，コンパスで導く**（4.4）: 学習の全体像を俯瞰できるよう（ReqDef 2.2），グラフはそのままマップとして見せ，ドリルダウン（F-007）で情報量を絞り，コンパス（F-013）で「次に進める場所」を示すことで認知負荷を抑える．当初は一本道に変換して見せる設計（旧 F-005, F-008）であったが，v0.5.0 でやめた．
2. **ノードをユーザーの持ち物としてマップ間で共有する**（4.1，ADR 0003）: 共有するのはノードの内容（タイトル，概要，サブノード）と進捗であり，道・メインノードかどうか・重要度はマップごとに持つ．マップを追加しても他のマップのグラフは変わらず，コンパスは1つのマップの範囲で計算できる．
3. **生成は DB を唯一の正とするバックグラウンドジョブにする**（4.2，4.3，ADR 0004）: ノード単位でストリーミング生成して保存し，クライアントへは DB から送る．接続が切れても生成は続き，保存したノードと送ったノードは常に一致する．
4. **業務ロジックと鍵はバックエンドだけが持つ**（4.6，4.8，4.10）: フロントエンドと CLI は API の結果を表示するだけにし，コンパスや検証を再計算しない．Web と CLI で表示が食い違わず，LLM の API キーや OAuth のシークレットがクライアントに出ない．

システムの構成は基本設計書 2章に示す．

## 4. 設計上の判断

各節は「決めたこと → 理由 → 比べた案」の順に書く．仕様は節の冒頭に示す基本設計書の節にある．

### 4.1 データ構造

仕様：基本設計書 5章．

**グラフはリレーショナル DB のノード・道テーブルで持つ**

* **案A（採用）**: MySQL 上にノード・道のテーブルを設けてグラフを表現する．
  * 利点: 既存の技術スタック（MySQL）をそのまま使え，スモールスタート（100〜1,000 DAU，ReqDef 5.2）の規模では十分な性能が出せる．マップ単位でのトランザクション管理も容易．
  * 欠点: 深い階層の依存関係探索（多段階のJOIN）はグラフDBほど高速ではない．循環を DB で防げないため，生成時と編集時に検証する（基本設計書 5.6）．
* **案B（不採用）**: Neo4j 等の専用グラフDBを導入する．
  * 利点: 依存関係の探索・パス検索がネイティブに高速．
  * 欠点: インフラ構成が複雑化し，初期リリースの規模に対して過剰投資である．ノード数・道の数が大幅に増加する場合は再検討の余地を残す．

**派生データを保存しない**

並び順（`display_order`）のような派生データは持たず，コンパス候補と現在地は都度導出する．並び順は一本道ビューのためのもので，一本道ビューをやめた（4.4）ことで要らなくなった．

**ノードの共有（ADR 0003）**

ノードをユーザーの持ち物とし，マップ生成時に既存ノードを LLM に伝えて再利用させる．同じ内容を2回学ばずに済み，進捗がマップ間で自然にそろう．代わりに，プロンプトに既存ノードを含めるためノード数が増えるとプロンプトが長くなり（6章），マップが自分のノードを持たなくなるため削除や現在地の扱いが複雑になる．比べた案（v0.8.0 までのマップごとのノードと Embedding による提案・リンク，生成中の承認，生成後の重複除去）と，それぞれを採らなかった理由は ADR 0003 に記す．

**寄り道はノードにしない（ADR 0002）**

ゴールとの関係が薄いテーマは，ノードではなく寄り道（新しいマップの提案）とする．マップのノードがすべてゴールに必要なものになり，進捗・コンパス・ゴール到達の計算で例外を作らずに済む．v0.8.0 までのサブクエスト（脇道のノード）は，あらゆる計算で除外の特別扱いが必要だった．

**メインノードが別のメインノードの中にも現れてよい（ADR 0006）**

同じマップでメインノードが別のメインノードのサブノードにもなることを許し，「『A』の中にもあります」と印を付ける．生成と編集の検証で例外にしない理由は ADR 0006 に記す．

**カラムの型**

* `user_llm_credentials.provider` を ENUM にしないのは，会社を足すたびに DB を変えずに済むようにするためである．受け付ける会社はアプリケーション層で候補の設定ファイルと照らす．
* `user_llm_credentials.api_key` を TEXT にするのは，暗号文が平文より長くなるためである．
* `map_progress_events` は追記だけの記録で，履歴として残すため `updated_at` を持たない（4.4）．

**`maps.updated_at` は操作したマップだけを更新する**

`maps.updated_at` はマップ一覧の並び順と，最新のマップへの転送に使う（ADR 0007）．共有のノードの変更を，そのノードが登場するすべてのマップに伝える（Rails の `touch: true` など）と，学習者が開いていないマップが最新になり，一覧の先頭や転送先が学習者の意図とずれる．そのため，操作したマップの `updated_at` だけを明示的に更新し，`maps` の行が変わらない変更（ノードの保存，進捗，編集）でも更新する．

### 4.2 マップの生成

仕様：基本設計書 6.2〜6.4，7.2．

**ストリーミング生成**

* **案A（採用）**: LLMにノード単位でストリーミング生成させ，逐次DB保存・逐次描画する．
  * 利点: ReqDef 5.2 の「最初の一歩をすぐに読み始められる」を満たす．
  * 欠点: ノード単位でのJSONパースと，途中で失敗したときの扱いが複雑になる．失敗の扱いは，SSE が DB から保存済みのノードだけを送り，途中で失敗したマップは `failed` として残す（削除して作り直す）ことで，ロールバックを不要にした（4.3）．
* **案B（不採用）**: マップ全体を一括生成してから一度にレスポンスする．
  * 利点: 実装がシンプルで，JSON全体の整合性検証がしやすい．
  * 欠点: 生成に数十秒かかる間ユーザーが何も見えない．
* **応答時間の実測**（プロトタイプ，モデル `gemini-3.1-flash-lite`）: スタンダードは全体で6〜10秒，ディープは36〜46秒かかった．ストリーミングなら，最初のノードは4〜12秒で届く．ディープを一括生成すると40秒前後何も見えないため，ストリーミングが必要という判断を裏づける．

**既存ノードの一覧を LLM に渡して再利用させる**

同じ内容のノードを見つける方法として，生成時に既存ノードの一覧（ID，タイトル，サブノードの ID）をプロンプトに含め，LLM に再利用させる．追加の API 呼び出しが要らず，ゴールの違いなどの文脈まで踏まえて判断できる．v0.8.0 までは Embedding の類似度で関連ノードを検出して提案していたが，閾値の調整が要り，マップごとにノードを別々に持つ前提だったため，ノードの共有（4.1）に合わせてやめた．プロンプトが長くなる問題は 6章の論点とする．

**プロトタイプで決めた生成の規則**

Gemini を直接呼ぶプロトタイプ（ブランチ `prototype/llm-map-generation`．main にはマージしない）で確かめた結果から，次の規則を決めた．

* **`node_count_target` を範囲にして検証する**: 「目安」として伝えると，ディープでもメインノードが15個を下回った．そこで「必ず N 個以上 M 個以下」と指示し，範囲外を検証エラーにした．
* **サブノード数の目安を指示する**: `max_depth` は入れ子の上限にすぎず，それだけではディープでもサブノードがほとんどできなかった．目安は検証しない．
* **`from` は「知らないと理解できない前提」だけを表す**: 「先に学ぶと良い」と書くと，前提関係の薄いノードまで一列につながった．
* **再利用したノードの中身全体を書いてよい**: LLM は再利用したノードの既存のサブノードを書き直してくることがあったため，許すことにした．保存の側で既存のものを無視して新しいものだけを足す．書かれなかった既存のサブノードや道を消さないのは，そのノードが他のマップで学習中のことがあり，生成で中身を減らすと他のマップの学習が壊れるためである．
* **ゴールへつながらないノードを検証エラーにする**: ゴールに関係のないノード（例：Git）が孤立してできた．出力の最後のメインノードをゴールとみなすのは検証のためだけで，順番やゴールのノードは保存しない（ゴール到達はすべてのメインノードの完了で決める．4.4）．
* **分岐の形を無理に作らせない**: Gemini は「並べて学べる」ことを，分岐ではなく `from` が空のメインノードを増やすことで表した．
* **「ノードを自分のサブノードへ道で結ぶ」出力は検証エラーにしない**: 内容の一部を順番の関係として書いた誤りであり，プロンプトで避けさせる．ただし誤っても，完了をユーザーが決めるため学習は止まらない（4.4）．
* **件数を JSON Schema の `minItems` / `maxItems` で強制しない**: Gemini では，入れ子が深いほど，件数の値が大きいほど，スキーマが `400 INVALID_ARGUMENT` で拒否され，スタンダード以上で使えなかった（Gemini に特有の点）．
* **再生成では前回の出力と検証エラーを会話の続きとして渡す**: 同じプロンプトで作り直すと，3回とも同じ孤立ノードが出た．ただし，ノード単位で保存・送信したあとの再生成は，同じマップでやり直さない方針（4.3）とぶつかる（6章）．

再利用したノードに中身全体を書かせる規則と，会話の続きとしての再生成は，プロトタイプでも実際の Gemini では動かしていない．実装後に実際の呼び出しで手動で確かめる（基本設計書 8章）．

### 4.3 生成ジョブと接続の切断

仕様：基本設計書 6.4.6，7.1（SSE イベント形式）．

**接続が切れても生成を続ける（ADR 0004）**

生成を SSE のリクエストから切り離したバックグラウンドジョブで行い，接続が切れても最後まで続ける．生成中に S-02 を再読み込みしたり離れたりするのは普通に起き，それで生成が壊れないようにするためである．Web でページを離れても，CLI で Ctrl+C を押しても，バックエンドからはどちらも「SSE 接続が切れた」にしか見えないため，区別せず同じ扱いにする．SSE が切れたら生成も止める案（Rails の `ActionController::Live` の既定の動き）は最も単純だが，再読み込みやタブの誤操作でも生成が中断されるため採らなかった．代わりに，ジョブ，SSE のつなぎ直し，ジョブが消えたことの検知（ハートビート）が要る．

**DB を唯一の正とする**

ジョブはノードを DB に保存するだけで，SSE は DB から読んで送る．保存したノードと送ったノードが常に一致し，途中で失敗したときのロールバックが要らない．

**つなぎ直しは保存済みのノードを全部送り直す**

* 採用：接続のたびに保存済みのノードを全部送り，クライアントが ID で上書きする．
* `GET /api/maps/:id` のポーリング：ノードが1つずつ現れる表示（F-009）を失うため採らない．
* `Last-Event-ID` による途中からの再開：再読み込みでは結局すべてを取り直すことになり，イベント ID の管理が増えるだけのため採らない．

**ジョブの実行方式**

プロトタイプ（`prototype/q4-generation-job` ブランチ）で比べ，ActiveJob の `:async` アダプタ（Rails 標準．Web サーバーのプロセス内のスレッドプール）を採用した．gem もプロセスも増えない．プロセスの再起動・デプロイでジョブは消えるが，ハートビートで `failed` として検知する．

* `Thread.new`：`:async` と同じくプロセス内で動くが，例外の記録や DB 接続の返却を自分で書く必要がある．
* Solid Queue：ジョブが DB に残り再起動後に再実行できるが，gem・ワーカープロセス・キュー用テーブルが増える．LLM のストリームは途中から再開できないため，再実行しても最初からやり直すことになり，すでに送ったノードと食い違う．得られるのは「失敗に早く気づける」ことだけで，それはハートビートで足りる．
* 必要になれば，`queue_adapter` の設定を変えて移行する．

**行ロックと状態の確認**

ノードの保存とマップの削除はどちらも最初に `maps` の行をロックする．ノード1つ分の書き込みが全部入るか全部入らないかのどちらかになり，削除と同時に起きても中途半端なノードが残らない．ロックの後に `status` が `generating` かを確かめるのは，ハートビート切れで `failed` にされた後に，遅れて動いたジョブが書き込むのを防ぐためである．

**失敗したマップはやり直さない**

LLM のストリームは途中から再開できず，同じマップでやり直すと最初から生成し直すことになり，すでに保存して送ったノードと食い違う．そのため，生成のやり直しや再開は設けず，削除して作り直すよう案内する．既存ノードの再利用（4.2）により，始めたノードの進捗は新しいマップに引き継がれる．

**ジョブの引数にキーを入れない**

ジョブにはマップだけを渡し，利用者のキーは始まったときに DB から読む．ActiveJob は引数をシリアライズし，既定でログに出すためである．

### 4.4 現在地とコンパス

仕様：基本設計書 6.6，3.2.2.6，4.4．

**一本道ではなくコンパスで導く**

v0.5.0 までは，グラフを生成直後にトポロジカルソートで一本道に並べ（`display_order`），その順で見せていた（表示のたびにフロントエンドで並べる案は，同順位のノードの順序が揺れるため採らなかった）．v0.5.0 で一本道ビュー（旧 F-005, F-008，ReqDef v1.2.0）と `display_order` をやめ，グラフはそのまま見せて全体を俯瞰できるようにし（ReqDef 2.2），コンパスが「今進める場所」をすべて指す形にした．CLI でもノードを学習順に見える一列として表示しないのは，同じ理由である．

**コンパスは案内であり，制限ではない**

候補でないノードも開始でき，完了はいつも学習者が決める．システムが自動で完了にしない．道は「おすすめの順番」であり，先のノードを開始できなくするものではない（GLOSSARY.md）ためである．`importance_score` は強調のためだけに使い，候補を絞らない．

**既知ノードは候補から外し，道の手前としては満たしたとみなす**

他のマップで完了したノードは，ある程度理解しているものとして扱う．

学習中のノードは，どのマップでも既知ノードにしない．別のマップで学習中のノードは，他のマップのコンパスではまだ学んでいないものとして候補に出るが，単純さを選んだ．

比べた案は，学習中にしたマップを進捗に記録し（`progress_statuses` の列），そのマップでは「今取り組んでいる」もの，他のマップでは既知ノードと分ける形である．しかし，記録したマップを削除すると，そのノードをどのマップで始めたものとみなすかを決める必要があり，他のマップで既知でなくなることを削除の前に知らせる注意も要った．進捗はマップ間で共有なのに，学習中だけマップごとの扱いを持つことになり，規則と画面が複雑になるため採らなかった（#53）．

**現在地は進捗の履歴から導出する（ADR 0005）**

v0.11.1 までは現在地をマップごとに1つ保存していた（`maps.current_node_id`）．ノードの編集（F-018）でメインノードを外せるようになり，外したノードや未着手に戻したノードが現在地だったときに「前の現在地」へ戻す必要が出たため，マップごとに進捗の更新の記録を追記し（`map_progress_events`），そこから導出する形に変えた．記録を消さないため，将来の履歴表示にも使える．記録が増え続け，現在地を求めるたびに集計が要るが，マップごとの索引で対応する．置き場所ごとの最終更新日時を持つ案も比べたが，過去の出来事が残らない．比較の詳細は ADR 0005 に記す．

**コンパスは生成が終わってから出す**

生成の途中では，後から届くノードや道で候補が変わるため，`ready`（`done`）になってから返す．

**コンパスはバックエンドで決める**

フロントエンドは返った値をそのまま表示し，CLI はそのまま出力して，どちらも再計算しない．Web と CLI で表示が食い違わないようにするためである（3章の4）．

### 4.5 ノードの編集

仕様：基本設計書 6.7，3.2.2.7，4.7．

* **`ready` のマップでだけ編集できる**: `generating` のマップでは生成ジョブがノードを保存している途中であり，`failed` のマップは削除して作り直す方針（4.3）のためである．
* **メインノードを外したときに道をつなぎ直さない**: 前後の道をつなぎ直すと，利用者の意図しない順番ができる．
* **元ノードから作ったマップの編集で，元ノードのサブノードも変える**: 生成時と同じく，元ノードをドリルダウンした中身と，元ノードから作ったマップの中身をそろえるためである．
* **既存ノードの提案に LLM や Embedding を使わない**: 提案は利用者が見て選ぶため，タイトルの部分一致のように判定が粗くても誤った再利用にはならない．別のメインノードの中にあるノードに「『A』の中にもあります」と添えるのは，そのノードへ道をつなぐ選択肢に気づけるようにするためである（ADR 0006）．
* **確認が要るかはバックエンドが判定する**: 他のマップに反映される編集や進捗のあるノードの削除で確認を挟む規則を，Web と CLI で同じにするためである．
* **同時の編集は後から保存したほうが勝つ**: 1人で使うアプリで衝突はまれなため，初期リリースでは防がない．防ぐ方法は 6章の論点とする．Web は画面に戻ってきたときに最新を取り直すことで，気づけるようにする（4.7）．

### 4.6 API

仕様：基本設計書 7.1，`api/openapi.yaml`．

**API の形の正は `api/openapi.yaml` のスキーマだけとする**

基本設計書には振る舞いだけを書き，JSON の例は書かない．手で書いた例はスキーマとずれ得る余計な状態になるためである．テストでもスキーマだけを正にする（4.11）．

**OpenAPI 3.0.3 で書く**

`committee`（5.6.4，2026/10/12 に確認）は 3.1 以上のファイルを読み込むとエラーにする（3.1 への対応は内部の openapi_parser で進んでいるが，まだリリースされていない）．`openapi-typescript`，`oapi-codegen`（v2.7.2 以降），Prism は 3.1 も読める．4つとも 3.1 以上を読めるようになったら，3.1 か 3.2（SSE を `itemSchema` で書ける）に上げてよい．

**エラーの文言は保存せず，コードから作る**

失敗したマップには `generation_error_code` だけを保存し，応答のたびに「コード→文言」の対応表から文言を作る．理由は3つある．

1. 例外のメッセージをそのまま保存・表示してしまう事故（内部の詳細や API キーの断片の漏えい）を構造上起こさない．
2. 文言を直したときに，過去に失敗したマップの表示にも反映される．
3. SSE と REST で同じ表現になる．

**CLI は API のエラーをそのまま出す**

文言をバックエンドの対応表にだけ置き，CLI と2か所に書いてずれるのを防ぐ．CLI の動き（終了コード，トークンファイルの削除）は `code` で分ける．

### 4.7 画面

仕様：基本設計書 3章，6.8．

**マップ一覧はサイドバーにする（ADR 0007）**

一覧の画面をやめ，S-01・S-02・S-05 に出すサイドバーにした理由は ADR 0007 に記す．サイドバーはマップを切り替えるためのもので，情報を増やさない（ReqDef 5.1）．注記，削除，進捗を出さないのはそのためである．

**広い画面ではサイドバーを重ねずに並べる**

重ねると，次の3つが起きる．

1. 最初の視点（現在地とその周辺）がサイドバーの下に隠れてずれる．
2. 「全体を表示」で収めた範囲の一部が隠れてずれる．
3. 隠れたノードを操作できない．

狭い画面では重ね，マップを選んだときだけ自動で閉じる（選んだマップが隠れないように）．

**開いている S-02 は，画面に戻ってきたときだけ取り直す**

Campass は1人で使うアプリで，ほかの場所（CLI，別のタブ）での変更は，利用者がそちらにいる間に起きる．戻った瞬間に取り直せば，ほとんどの場合に足りる．定期的なポーリングやプッシュで「このマップが変わったか」を調べるには，ノードがマップ間で共有なので（ADR 0003）共有のノードの変更まで追う必要があり，仕組みが重くなる．困るのは，ブラウザを一度も操作せずに2つの画面を並べて見ている場合だけである．端末からブラウザのウィンドウに戻ったときは `visibilitychange` が起きないため，`focus` でも判定する．

マップ一覧は，サイドバーに生成の状態と削除をすぐ反映するため，開いている間だけ30秒ごとに取得する．閉じている間は一覧が見えないので取得しない．

**パンくずリストを作らない**

マップ間ノードや元ノードにより，同じマップへ複数のマップから来られる．固定の階層を表すパンくずは成り立たないため，ブラウザの戻ると「← 来たマップへ戻る」だけにした．

### 4.8 CLI

仕様：基本設計書 4章，7.4．

**実装言語は Go**

* **案A（採用）**: Go で実装する．
  * 利点: 単一の実行ファイルとして各OS向けに配布でき，利用者が実行環境を用意する必要がない（ReqDef 5.1）．HTTP クライアントと SSE の受信を標準ライブラリだけで書ける．
  * 欠点: フロントエンド・バックエンドと型定義を共有できない．API とのずれは，OpenAPI からの型の生成と Prism の検証で補う（4.11）．
* **案B（不採用）**: TypeScript（Node.js）で実装する．
  * 利点: フロントエンドと API の型定義や API 通信層を共有できる．
  * 欠点: 利用者に Node.js が必要になり，単一の実行ファイルにするには追加のツールが要る．
* **案C（不採用）**: Ruby で実装する．
  * 利点: バックエンドと言語を揃えられる．
  * 欠点: 利用者に Ruby の実行環境が必要になる．

**コマンドの解析は cobra**

* **案A（採用）**: `github.com/spf13/cobra` を使う．
  * 利点: サブコマンドが多く（`node add`，`sub path add` のように入れ子にもなる），その定義・ヘルプ・引数の検査をまとめて書ける．bash / zsh / fish / PowerShell の補完を生成でき，Homebrew と deb / rpm に同梱できる．
  * 欠点: 外部パッケージへの依存が増え（cobra と，cobra が使う `spf13/pflag`・`inconshreveable/mousetrap`），その更新・脆弱性対応が要る．
* **案B（不採用）**: 標準ライブラリの `flag` で書く．
  * 利点: 外部パッケージに依存しない．
  * 欠点: サブコマンドの振り分け，入れ子のサブコマンド，ヘルプ，補完を自分で書くことになり，コマンドが増えるほどコードと誤りが増える．

依存をこれ以上増やさないのは，単一の実行ファイルとして配布しやすくし，依存パッケージの更新・脆弱性対応の負担を小さくするためである．

**CLI は業務ロジックを持たない**

コンパス，検証，再利用はバックエンドだけが行い，CLI は返った結果をそのまま出力する．Web と CLI で結果が食い違わないようにするためである（3章の4）．

**出力は JSON にし，対話は持たない**

CLI の主な利用者は，人ではなく AI や他のサービスである．人が見て分かりやすい表示は Web が受け持つ．

* **案A（採用）**: API のレスポンスの JSON をそのまま出力し，入力は引数とフラグだけにする．利用者の判断が要るとき（実行前の確認，既存ノードの提案）は，内容を出して決まった終了コードで終わり，フラグを付けて実行し直させる．
  * 利点: AI や他のサービスが出力をそのまま読める．対話の入力を待って止まらない．出力の形が `api/openapi.yaml` のスキーマと同じなので，CLI 独自の形を決めて保つ必要がない．テキストの表示を作らない分，コードとテストが減る．
  * 欠点: 人がターミナルで読むには向かない．
* **案B（不採用）**: JSON を既定とし，`--human` を付けたときだけ人向けのテキストと対話にする．
  * 利点: 人も CLI を使いやすい．
  * 欠点: 2つの出力の形と対話の両方を作り，試し続ける必要がある．主な利用者は使わない．
* **案C（不採用）**: 人向けのテキストと対話を既定とし，`--json` を付けたときだけ JSON を出す（v1.0.0 までの設計に近い）．
  * 利点: 人がそのまま使える．
  * 欠点: 主な使い方で毎回フラグが要る．`y/N` の確認や番号での選択に AI が答えられず，止まってしまう．

**`401` で自動的にログインを始めない**

スクリプトから呼ばれたときに，ブラウザでの許可を待って止まってしまわないようにするためである．トークンファイルを消して終了コード 1 で終わる．

**タグに `cli/` を付ける**

同じリポジトリのほかの部分（`backend/`，`frontend/`）のタグと分けるためと，サブディレクトリにある Go モジュールのタグの決まり（モジュールのディレクトリ名を前に付ける）に合わせるためである．

### 4.9 認証

仕様：基本設計書 7.3，7.4．

**(1) Web のセッションの持ち方：Cookie セッション vs トークン方式**

* **案A（採用）**: ランダムなセッショントークンを `HttpOnly` の Cookie に入れる．
  * 利点: JavaScript からトークンを読めないため，XSS があってもトークンそのものは盗まれない．`EventSource` はヘッダーを付けられないが，Cookie なら SSE もそのまま認証できる．
  * 欠点: Cookie はブラウザが自動で送るため，CSRF の対策（CSRF トークンと `Origin` の確認）と CORS の設定が要る．
* **案B（不採用）**: CLI と同じトークンを SPA が保存し，`Authorization: Bearer` で送る．
  * 利点: CSRF の対策が要らず，バックエンドの認証の仕組みを CLI と1つにできる．
  * 欠点: トークンを `localStorage` などに置くと，XSS で読み出される．SSE は `EventSource` を使えず，`fetch` でストリームを読む処理を自分で書くことになる．

**(2) ログイン方法：Google / GitHub だけ vs パスワードも残す**

* **案A（採用）**: Google と GitHub のアカウントだけでログインする．
  * 利点: パスワードを保存しないため，パスワードの漏えい・使い回し・リセットの仕組みを考えなくてよい．登録画面が要らない．Web でログインできれば，CLI も Web のログインに乗せられる．
  * 欠点: どちらのアカウントも持たない人は使えない．Google / GitHub が止まるとログインできない．
* **案B（不採用）**: メールアドレスとパスワードのログインも残す．
  * 利点: 外部のアカウントを持たない人も使える．
  * 欠点: パスワードのハッシュ，リセットのメール送信，メールアドレスの確認が要り，実装と運用の負担が大きい．外部アカウントとまとめるときの確認も複雑になる．

**(3) 配信の形：別オリジン・同じ親ドメイン vs 同じオリジン vs まったく別のドメイン**

* **案A（採用）**: `app.` と `api.` のように，同じ親ドメインのサブドメインに分ける．
  * 利点: フロントエンドとバックエンドを別々に配信・デプロイできる．別オリジンだが同じサイトなので `SameSite=Lax` の Cookie が送られ，サードパーティ Cookie の制限を受けない．開発環境（`localhost:5173` と `localhost:3000`）もポートが違うだけで同じサイトになり，同じ形で動く．
  * 欠点: CORS の設定（`credentials` つき）と，書き込みの `Origin` の確認が要る．
* **案B（不採用）**: 同じオリジンにまとめる（Rails が SPA も配信する，またはリバースプロキシで `/api` を振り分ける）．
  * 利点: CORS が要らず，Cookie の扱いが最も単純．
  * 欠点: 配信の仕組みが1つにまとまり，フロントエンドだけを CDN などで配信しにくい．開発環境でもプロキシの設定が要る．
* **案C（不採用）**: まったく別のドメインに置く．
  * 利点: 配信先を自由に選べる．
  * 欠点: バックエンドの Cookie がサードパーティ Cookie になり，送られないブラウザがある．

**(4) OAuth の実装：omniauth vs 自前で書く**

* **案A（採用）**: `omniauth`，`omniauth-google-oauth2`，`omniauth-github` と `omniauth-rails_csrf_protection` を使う．
  * 利点: `state` の確認，PKCE，トークンの交換，プロフィールの取得を広く使われた実装に任せられる．Rails で標準的な方法で，テスト用のモックもある．
  * 欠点: omniauth 関連の gem が4つ増える．omniauth はセッションを使うため，API モードで外したミドルウェアを戻す必要がある．
* **案B（不採用）**: OAuth 2.0 の処理を標準ライブラリ（`Net::HTTP`）で自前で書く．
  * 利点: 依存が増えない．
  * 欠点: `state` や PKCE の確認など，誤るとそのまま脆弱性になる処理を自分で書いて保守することになる．

**(5) セッションの保存先：DB の自前テーブル vs `activerecord-session_store` vs `api_tokens` とまとめる**

* **案A（採用）**: `web_sessions` を作り，トークンのハッシュ，有効期限，最終利用時刻を持つ．
  * 利点: ハッシュだけを保存するため，DB が漏れてもセッションは使えない．その端末だけのログアウト，30日のスライド式の期限を素直に書ける．将来の「ログイン中の端末の一覧」にも使える．gem が要らない．
  * 欠点: セッションの発行・確認・延長を自分で書く．
* **案B（不採用）**: `activerecord-session_store` で Rails のセッションを DB に置く．
  * 利点: Rails のセッションの仕組みをそのまま使える．
  * 欠点: gem が増える．セッションの中身をそのまま保存し，ユーザーとの対応やスライド式の期限を扱うには結局手を入れる必要がある．
* **案C（不採用）**: `api_tokens` にまとめ，種類を表すカラムで Web と CLI を分ける．
  * 利点: テーブルとトークンを確かめる処理を1つにできる．
  * 欠点: Web のセッションと CLI のトークンは，発行のしかた（Cookie か，レスポンスで渡すか），CSRF の検査の有無，`user_agent` と `name` のように持つ情報が違い，条件分岐が増える．

**(6) CLI の認証：トークン方式 vs Cookie セッション**

* **案A（採用）**: ログイン時に発行したトークンを `Authorization: Bearer` ヘッダーで送る．
  * 利点: CLI から扱いやすく，トークン単位で失効できる．DBにはハッシュのみを保存するため，DBが漏えいしてもトークンは使えない．
  * 欠点: トークン発行・失効の API と `api_tokens` テーブルが追加で必要になる．
* **案B（不採用）**: フロントエンドと同じ Cookie セッションを CLI でも使う．
  * 利点: バックエンドの認証の仕組みを1つにできる．
  * 欠点: CLI 側で Cookie と CSRF 対策を扱う必要があり，実装が複雑になる．

**(7) CLI のログイン：パスワード入力 vs ローカルへのリダイレクト vs デバイスコード**

Web のログインを Google / GitHub だけにしてパスワードを廃止したため，`campass login` がトークンを受け取る方法を比べた．

* **案A（不採用）**: CLI でメールアドレスとパスワードを入力させる（v0.13.0 までの設計）．
  * 利点: ブラウザが要らず，ターミナルだけで済む．
  * 欠点: Campass はパスワードを持たないため，そもそも使えない．仮にパスワードを残しても，入力中に表示しないためのエコー制御を OS ごとに書く必要があり，標準ライブラリだけでは Windows を含めて扱いにくい．
* **案B（不採用）**: CLI が `localhost` で一時的な HTTP サーバーを立て，ブラウザでのログイン後にそこへリダイレクトさせてトークンを渡す．
  * 利点: 利用者はブラウザでログインするだけで，コードを打たなくてよい．
  * 欠点: CLI と同じマシンでブラウザを開く必要があり，SSH 先やコンテナの中では使えない．ポートの確保，リダイレクト先の検証，`state` の確認を CLI とバックエンドの両方で書く必要がある．
* **案C（採用）**: RFC 8628 のデバイスコード方式．CLI が表示したコードを，利用者がブラウザの S-03 に入力して許可する．
  * 利点: ブラウザは別のマシンでもよいため，SSH 先やコンテナの中でも使える．CLI はパスワードを扱わず，エコー制御が要らない．Web のログイン方法（Google / GitHub など）が変わっても CLI は変わらない．CLI 側は標準ライブラリ（`net/http`，`os/exec`，`os/signal`）だけで書ける．
  * 欠点: 利用者がコードを打つ手間がある．ログイン要求のテーブル（`cli_login_requests`），4つの API と照会の API，S-03 の画面が増える．

**細かな判断**

* **ログインの判定は `provider` + `provider_uid` で行う**: メールアドレスは Google / GitHub 側で変わることがあるためである．
* **確認済みのメールアドレスでだけユーザーをまとめる**: 乗っ取りを防ぐためである．他人のメールアドレスを確認せずに登録できるサービスでそのアドレスを名乗れば，まとめた先のユーザー（他人のマップとノード）にログインできてしまう．
* **セッション・トークン・`device_code` はハッシュだけを保存する**: DB が漏れても使えないようにするためである．
* **ログイン後に Rails 標準の一時的なセッションをリセットする**: セッション固定を防ぐためである．
* **Cookie を `SameSite=Strict` にしない**: Google / GitHub から `api.` のコールバックへ戻る遷移で，Rails 標準のセッションの Cookie（`state`）が送られる必要があるためである．
* **Bearer トークンのリクエストを CSRF の検査の対象外にする**: ブラウザが他のサイトから勝手に `Authorization` ヘッダーを付けることはできないためである．認証なしの CLI のログイン要求の作成と受け取りも，Cookie を使わないため対象外にする．
* **ログインは POST のフォーム送信で始める**: GET でログインを始められると，他のサイトから勝手にログインを始めさせられるためである．
* **`return_to` をパスに限り，転送先のオリジンを `FRONTEND_ORIGIN` に固定する**: オープンリダイレクトを防ぐためである．
* **`verification_uri` に `user_code` を含めない**: 含めると，攻撃者が自分の端末でログインを始め，そのリンクを利用者に踏ませて「許可」させれば，攻撃者の CLI が利用者のトークンを受け取れてしまう．利用者に自分のターミナルのコードを打たせることで，自分が始めたログインだけを許可させる．同じ理由で，`user_code` を URL に残さないよう `lookup` も POST にする．
* **期限の延長の書き込みは1日に1回まで**: リクエストのたびに書き込むと，読むだけのリクエストにも DB への書き込みが毎回加わる．代わりに，期限は実際の最後の利用より最大1日早く切れ得る．

### 4.10 LLM の呼び出しと利用者のキー

仕様：基本設計書 7.2，3.2.5，6.4.6．

**LLM の抽象インタフェースを置く**

外部サービスへの依存を小さくし，LLM を替えても変わる範囲をインタフェースの実装だけにするためである．役割を「生成する」と「キーとモデルを確かめる」の2つに絞り，ノードの切り出し，検証，保存は LLM の種類に関係なく共通にする．使うキーとモデルを外から渡すことで，実装はサービスのキーか利用者のキーかを知らずに済み，生成ジョブのテストでは偽物を差し込める（4.11）．

**Gemini は Faraday で直接呼ぶ**

`google-genai` gem（0.1.1）は，ストリーミングも `systemInstruction` も扱えないため使わない．Faraday は `google-genai` の依存としてすでに入っており，新しい gem は増えない．`google-genai` gem を Gemfile から外すかどうかは #20 の範囲外とし，後で決める．キーを URL のクエリ（`?key=`）ではなく `x-goog-api-key` ヘッダーで渡すのは，URL を記録するログにキーが残らないようにするためである．

**学習に使わせないことは API のプランで守る（ReqDef 5.3）**

リクエストに設定を付けることも，送信前の検証もしない．Gemini API にはリクエストごとの項目がないためである．代わりに，本番では学習に使わない契約のプランのキーだけを使い，デプロイの手順で確かめる．

* **Gemini**: 有料のサービス（Paid Services），つまり請求先のアカウントを有効にした Cloud プロジェクトを通した呼び出しでは，プロンプトと応答を製品の改善に使わない．ただし，禁止されている使い方を見つけるためだけに，限られた期間ログに残す．無料のサービス（Unpaid Services）では，入出力を製品の改善と開発に使い，人が読むこともある．したがって本番のキーは，請求先を有効にしたプロジェクトで作る．請求先を有効にしたプロジェクトの無料の枠の中の呼び出しがどちらに当たるかは，規約に明記がないため，有料のサービスに当たるとは決めない．規約: https://ai.google.dev/gemini-api/terms （2026/10/12 に確認．ページの最終更新は 2026/04/28）
* **OpenAI / Anthropic**: 2社目として足すときに，各社の今の規約を確かめて追記する．

**利用者のキーが使えなかったら，サービスのキーに切り替えない**

黙って切り替えると，運営の費用が増え，学習に使わせない約束の範囲も利用者の知らないうちに変わるためである．また，キーが無効・上限に達したという失敗は，パースの失敗や検証エラーと違って同じキーでは直らないため，再試行しない．

**保存時のエラーと呼び出し時のエラーのコードを分ける**

保存のときの `api_key_invalid` は「いま入力したキー」を，呼び出しのときの `user_api_key_invalid` は「保存してあるキー」を確かめた結果である．利用者に求めることが違う（入力を直す／S-05 で設定を見直す）ため，コードを分ける．

**キーの確かめ方はモデルの一覧の API**

Gemini の `GET /v1beta/models` はモデルを動かさないため費用がかからない．代わりに，上限や支払いの問題で実際にモデルを動かせるかは確かめられない．その場合は最初の生成で `user_api_key_quota_exceeded` として知らせる．

**モデルは候補から選ばせる**

自由なモデル名を受け付けると，プロンプトや JSON Schema（4.2）が合わないモデルで生成が失敗するためである．

**キーの設定は Web からだけ**

キーを端末に入力させると画面に表示されてしまい，引数や環境変数で渡すとシェルの履歴やプロセスの一覧に残るためである（CLI でパスワードを扱わない理由（4.9 の (7)）と同じ）．

**キーの保存**

* Rails 標準の Active Record Encryption を使い，gem を増やさない．DB やバックアップが漏れても，暗号化の鍵がなければキーは読めない．
* 検索に使わないため，非決定的な暗号化にする．
* `config.filter_parameters` に `api_key` を明示する．Rails の既定の `_key` でも隠れるが，既定に頼らないためである．

### 4.11 テスト

仕様：基本設計書 8章．

* **API の形はスキーマだけを正にして確かめる**: 手で書いた JSON の例を正にすると，スキーマとずれ得る余計な状態になる．フィクスチャを共有の例にせず各テストに書くのは，場面ごとに必要な値が違い，例の置き場を増やすとスキーマとずれる状態が増えるためである．
* **生成ジョブのテストは Minitest で書く**: Rails 標準で，gem を増やさない．
* **ハートビートの上限を設定値にする**: テストはその値から境目を作り，上限を変えてもテストを直さずに済む．
* **並行実行は順番を固定して再現する**: 「たまたま同時に起きる」のを待つと，結果が実行ごとに変わる．
* **行ロックのテストは実際の MySQL で，トランザクションでの巻き戻しを切って動かす**: 行ロックは DB の機能であり，2つのスレッドが別の接続で同じ行を見るためである．

## 5. 懸念事項（Caveats / Security / Privacy Concerns）

* **APIキーの秘匿化**: 外部LLM APIキーと OAuth のシークレットはバックエンドだけが持ち，フロントエンドと CLI へは出さない（ReqDef 5.3）．リポジトリへのコミットを防ぐ仕組み（lint / pre-commit hook 等）の導入が要る．
* **学習データへの利用**: ユーザーの自由記述ワーク（興味・ゴールの入力等）に個人情報や機密情報が含まれる可能性がある．本番のサービスのキーは学習に使わない契約のプランのものだけを使い，デプロイの手順で確かめる（4.10）．利用者が自分の API キーで送る分はこの約束の対象外となるため，S-05 でそのことを示す（基本設計書 3.2.5.3）．
* **利用者の API キー（ReqDef F-020）**: 暗号化の鍵をなくすと保存したキーは読めなくなる．そのときは呼び出しを `user_api_key_invalid` にし，S-05 で設定し直してもらう（基本設計書 7.2）．鍵は DB とは別に保管する．
* **Web のログイン**: Cookie セッションを使うため，CSRF とオープンリダイレクトが主な脅威になる．CSRF トークンと `Origin` の確認，`FRONTEND_ORIGIN` だけを許す CORS，`return_to` の制限で防ぐ．確認していないメールアドレスではユーザーをまとめない（4.9）．
* **CLI のトークン管理**: トークンはユーザーの端末にファイルとして保存されるため，所有者のみ読み書きできる権限（0600）で保存し，有効期限を設ける．30日使わなかった端末のトークンは使えなくなり，`campass logout` で失効できる（基本設計書 7.4）．
* **CLI のログイン**: 他人が始めたログインを許可させるフィッシングを，`user_code` を URL に含めないことと，S-03 で端末名と開始時刻を見せてから許可させることで防ぐ（4.9）．
* **プロンプトインジェクション対策**: ユーザーの自由入力がそのままLLMへのプロンプトに埋め込まれるため，システムプロンプトとユーザー入力を明確に分離し，構造化出力（JSON Schema／ツール呼び出し）を強制することで，意図しない指示の混入や出力形式の破壊を防ぐ．
* **マップのデータ保持**: マップ，ノードおよび学習ログはユーザーが自ら削除するか退会するまで永続保持する方針のため，退会時のデータ削除フロー（物理削除 or 論理削除）を別途明確にする必要がある（ReqDef 5.4）．
* **既存ノードの送信**: マップ生成のたびにユーザーの既存ノードのタイトルをLLMに送る．他ユーザーのノードは送らず，他のリクエストと同じキーで送る（4.10）．
* **生成コンテンツの信頼性**: LLMが生成する学習ステップの内容やリンク先には誤り・幻覚（hallucination）が含まれ得る．教材コンテンツ自体の制作を対象外としているため（2.2），外部リンクの生存確認や内容の正確性検証は当面ユーザーの判断に委ねる旨をUI上で明示する．

## 6. オープンな論点（今後議論が必要な事項）

* **既存ノード一覧のプロンプト長**: マップ生成時にユーザーの全ノードをLLMに渡すため（基本設計書 6.4），ノード数が増えるとプロンプトが長くなりコスト・レイテンシが悪化する．ゴールと関係の近いノードだけを渡す絞り込み（Embedding による選別等）をいつ・どう導入するか．
* **同時生成時のサブノード重複**: 2つのマップを同時に生成し，同じ再利用ノードにサブノードを追加すると，重複したサブノードができ得る．初期リリースでは対処しない．
* **マップ間ノードの共有解除**: 再利用が誤っていた場合に，ノードの共有を解除する機能を設けるか．
* **F-003 の見直し**: 後のフェーズで F-016（もっと詳しく）と F-017（ノードのマップ化）が入った後，最初に難易度を選ばせる必要があるか．
* **F-016 / F-017 の詳細**: 「もっと詳しく」で追加するサブノードの生成方法と API，ノードのマップ化の API と UI．元ノードから作ったマップを編集したときに元ノードのサブノードも変える規則（基本設計書 6.7）も，ここで合わせて確定する．
* **再生成と保存済みのノード**: 再生成（最大2回，基本設計書 6.4）は，前回の出力と検証エラーを渡して作り直させる．しかし，ノードは1つずつ保存して SSE で送るため（基本設計書 6.4.6），ゴールへつながらないノードやメインノード数の範囲のように最後まで受けないと分からない検証エラー（循環なども，見つかった時点で前のノードは保存済み）では，作り直すと保存して送ったノードと食い違う．同じマップでのやり直しはしない（4.3）ため，いつ再生成できるか（最初のノードを保存する前だけにする，保存済みのノードを残して続きを作らせる，など）と，保存済みのノード・送った SSE の扱いを決める必要がある．プロトタイプは DB に保存せず，全体を受けてから検証したため，この点は確かめていない．
* **生成中のマップと共有の編集**: 編集は `ready` のマップからだけ行えるが，内容やサブノードは共有のため，同じノードを再利用している別のマップが生成中のことがある．ユーザーがサブノードを外して削除した直後に，生成ジョブがそのノードを参照すると，未知の参照（基本設計書 6.4）として生成が失敗し得る．初期リリースでどこまで対処するか．
* LLM生成コンテンツの品質担保（幻覚対策）について，将来的にファクトチェック機構やユーザーフィードバックによる品質改善ループを設けるか．
* **期限切れの行の掃除**: 期限切れの `api_tokens`・`web_sessions`・`cli_login_requests` の行は消さず，使えないとするだけにしている（基本設計書 7.3，7.4）．今の設計には定期実行の仕組みがないため，行が増え続ける．いつ・どう消すか．
* **同時の編集の衝突**: 2か所から同じノードやマップを編集すると，後から保存したほうが勝つ（4.5）．防ぐなら，版の番号（Rails 標準の `lock_version`）を持たせ，古い版から保存しようとしたら `409` で断る方法がある．ただし，ノードはマップ間で共有なので（ADR 0003），どの行の版を比べるか（ノード，サブノード，道，マップ）の扱いが複雑になる．1人で使うアプリで衝突はまれなため，初期リリースでは対処しない．
* **CLI とバックエンドの互換性**: API を変えたときに古い CLI をどう扱うか（`User-Agent` のバージョンで断るか）と，新しい版が出たことを利用者にどう知らせるか（基本設計書 4.1，4.8）．
