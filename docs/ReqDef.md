## 2. プロジェクト概要
### 2.1 背景・目的
* **独学における挫折の解消**: 独学において発生しやすい「次に何を学べればいいかわからない」「今やっている基礎学習が何に繋がっているか見えず飽きてしまう」という課題を解決します．
* **本質的な理解の支援**: 表面的なツールの使い方（ハウツー）の習得に留まらず，その裏側にある原理・原則を深く学ぶための独学支援システムを構築します．
* **最適な学習順序の自動化**: ユーザーが目指す「最終ゴール」から逆算し，必要な前提知識を基礎から順番に積み上げていく「トップダウン逆算型ボトムアップ学習」のプロセスを提供します．

### 2.2 ゴール・目指す姿
* ユーザーが学びたいことを自由に入力するだけで，LLM（生成AI）が学習内容の依存関係を計算し，迷子にならない「パーソナライズされたマップ」を動的に生成・提示できる状態を目指します．
* 学習の全体像を「マップ」として俯瞰でき，その上で「コンパス」が今進める場所を指し示すことで，全体を眺めながらも進む方向を見失わない状態を目指します．用語は GLOSSARY.md に従います．

### 2.3 ターゲットユーザー
* **目的意識のある独学者**: 「AIについて深く知りたい」「デザインに興味がある」など，ある程度の興味の種や問題意識（ゴール）を持っているユーザー．
* **本質を追求したい学習者**: 単なるツールの操作方法だけでなく，技術の背景や原理原則まで深くステップアップして学びたいユーザー．

## 3. システム化の範囲（スコープ）
### 3.1 対象範囲（インスコープ）
* ユーザーの入力から，LLM のAPI を活用して学習カリキュラム（JSON）を動的に生成するバックエンド機能．
* 複雑なマップを認知負荷の低いUIに落とし込むフロントエンド画面の構築．
* フロントエンドと同じバックエンドAPIを利用し，ターミナルから学習を進められるCLIクライアントの構築．
* ユーザーの理解度や記述式回答，選択した難易度に応じて，プロセスを最適化・動的アップデートする機能．

### 3.2 対象外範囲（アウトスコープ）
* 独自のLLMモデルの構築（既存の外部LLM APIであるChatGPT やClaude やGemini などを活用することを前提とする）．
* 各学習ステップにおける，詳細な教材コンテンツそのものの独自制作（まずは外部記事へのリンクやAIによる概要生成，課題の提示を主軸とする）．

## 5. 非機能要件

機能面以外でシステムが満たすべき品質，性能，および運用の要件です．

### 5.1 動作環境（システム特性）
* **対応ブラウザ / OS:**
  * Google Chrome（最新版）
  * Microsoft Edge（最新版）
  * iOS Safari
  * Android Chrome
* **デバイス:** PC，スマートフォン（レスポンシブ対応）
* **CLI（F-014）:** Linux，macOS，Windows．実行環境のインストールを不要とするため，単一の実行ファイルとして配布する．
* **画面表示の最適化（認知負荷の軽減）:** * マップの初期画面ではメインノードのみを描き，視点を「現在地」とその周辺（現在地へ道がのびるノード，コンパスが指す今進める場所）に寄せて見せる画面設計とする．全体像はユーザーが能動的に広げて眺める．これにより，ユーザーが目にする情報量を絞り込み，独学時の認知負荷を最小限に抑える．

### 5.2 性能・拡張性
* **LLM API レスポンスのUX制御（ストリーミング処理）:**
  * マップの動的生成には数十秒の時間を要する可能性があるため，**ストリーミング形式（逐次生成・反映）**を採用する．AIが生成したノードからリアルタイムに画面へ描画し，ユーザーが最初の一歩をすぐに読み始められるようにすることで，体感待ち時間を極小化する．
* **同時接続数（スモールスタート仕様）:**
  * 初期リリース時は検証・スモールスタートを前提としたインフラ構成とする．
    * **通常時:** 100 アクティブユーザー / 日
    * **最大（ピーク時）:** 1,000 アクティブユーザー / 日
  * ※将来的な大規模公開やSNS等での拡散（バズ）に伴うアクセス急増時は，パブリッククラウド（AWS等）のスケールアップ/スケールアウトにより柔軟に拡張できるインフラ構成（設計時の考慮）とする．
* **拡張性（データ構造の担保）:**
  * ユーザーが複数のゴールを並行して達成できるよう，同じ内容のノードを複数のマップで共有できるデータ構造（グラフ構造の表現が可能なリレーショナル設計等）を定義する（F-015）．

### 5.3 セキュリティ・データ保護
* **API キーの秘匿化:**
  * 外部LLM（OpenAI, Anthropic等）のAPIキーは必ずバックエンド側（サーバーサイド）で安全に管理し，フロントエンドおよびCLI（クライアント側）へ絶対に露出させないこと．
* **データ保護（オプトアウトの必須化）:**
  * ユーザーの自由記述ワーク（言語化入力）における個人情報や秘密情報の漏洩リスクを防ぐため，外部LLM APIへの送信時には「入力データをAIモデルの学習に利用させない（オプトアウト）」設定を必須とし，API経由でのデータプライバシーを担保する．

### 5.4 運用・保守
* **プロンプトのバージョン管理:**
  * AIへの指示文（プロンプト）の変更は，生成されるマップの品質やデータ構造（JSON）に直結するため，ソースコードとは完全に切り離してバージョン管理を行う（LangChain/LangSmith等のオーケストレーションツールの活用，または外部管理ファイルの採用）．これにより，システムを無停止のままプロンプトのA/Bテストやプロンプトチューニングの改善を容易にする．
* **マップのデータ保持期間:**
  * ユーザーが作成した複数の「マップ」，およびそれに紐づく「動的な学習ログ・進捗ステータス」は，ユーザーが自ら削除するか，退会するまでデータベース上に永続保持する．
